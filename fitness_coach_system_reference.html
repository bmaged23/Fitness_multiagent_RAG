System overview

Coach is the trainee-facing deepagents main agent. It owns the conversation, identity resolution, and long-term memory, and delegates to Retriever and Program Designer as subagents. Both subagents can call Retriever directly against Qdrant; Designer is the only agent that writes plans, backed by the SQLite trainee database.

Design principles established

Retriever doesn't reason about fitness
Only job is search quality — decomposition, adaptive chunk count, coverage validation, retry.
Designer synthesizes, doesn't just select
Combines multiple retrieved programs — trades flexibility for a coherence-guard requirement.
Coach routes by reasoning, not classifier
Designer is just an available tool; Coach's own judgment decides when to call it.
Persistent facts live in one place
Injuries/equipment/goals live in trainees, not duplicated per plan or per memory summary.
Memory is rolling, not accumulating
One row per trainee in coach_memory — summarized and salience-truncated, not appended forever.
Every revision is audited
plan_revisions keeps a full before/after snapshot of every patch, with what triggered it.
subagent

Retriever agent

Callable by both Coach and Program Designer. Doesn't reason about fitness — its only job is accumulating enough grounded context to satisfy an information need, then handing back chunks with a confidence flag.

Accumulate-and-expand retrieval loop

Not a single retry loop — tracks coverage of the overall information need across sub-queries, expanding when gaps remain even after some sub-queries already succeeded.

  1. Decompose the needSlot-based extraction first (goal, equipment, difficulty, duration) — falls back to free-form LLM coverage judgment when the query doesn't map to slots cleanly (e.g. "why am I sore for 3 days").
  2. Pick next unaddressed need, query QdrantChunk count is adaptive to query specificity, not a fixed top-k.
  3. Validate against that specific needRelevant and sufficient, or noise?
  4. Sufficient → save to accumulated pool, mark need satisfied
  5. Insufficient → rewrite query, retry same needPer-need retry, not a global retry counter.
  6. Re-check overall coverageGiven everything accumulated, is the original query now answerable? If not, formulate a new sub-query for the gap.
  7. Self-assess or hit ceiling → returnModel can surrender early if it believes coverage is sufficient; hard ceiling underneath as a safety net against runaway loops.
Hard ceiling5–6 total retrieval steps per invocation
CallersCoach (open-ended questions) + Designer (structured plan queries)
OutputAccumulated chunks + confidence flag

Turns a goal plus retrieved chunks into a strict JSON plan. Synthesizes across multiple retrieved programs rather than selecting one, which means it needs a coherence guard.

  1. Classify requestNew plan, or a revision to an existing one.
  2. New plan → call Retriever, then synthesize a draft by combining chunks across multiple retrieved programs.
  3. Revision → check plan.md/context first for what's needed (e.g. a knee-safe substitute); only call Retriever if that comes up empty.

main agent

Coach agent

Owns the conversation, identity, routing, and long-term memory. Uses Designer as a tool rather than a hardcoded classifier — Coach reasons out whether a message needs Designer or can be handled directly.

Session start — identity resolution

  1. Check identityName + secondary ID (phone / email / trainee_id).
  2. Match → returning traineeLoad trainees profile, latest coach_memory summary, active plan. Name match without secondary ID match is a confirmation prompt, not a silent load.
  3. No match → new traineeRun intake flow: name, contact, goals, equipment, injuries/limitations → write first trainees row.
  4. Check progress_logs for missed-session patternsIf flagged, Coach opens proactively instead of waiting to be asked.

Per-message loop

  1. Load contextProfile, memory, active plan.
  2. Reason: handle directly or route to DesignerDirect: general coaching / knowledge questions, Coach may call Retriever itself. Routed: anything touching the plan.
  3. Interim acknowledgment before delegatingSent before a multi-step Retriever/Designer chain runs, so the trainee isn't staring at silence for 15–20s — the "keep them engaged" requirement.
  4. RespondRelays Designer's structured output in trainee-facing language, or answers directly.
  5. Update memoryFull pipeline below. Also writes progress_logs if the message contained loggable info.

Long-term memory pipeline

Rolling, summarized, salience-truncated — one row per trainee, not one per session. Persistent facts (injuries, goals, equipment) live in trainees separately; this is conversational/relational context only.

deepagents wiring

Using the framework's primitives beyond plain tool-calling — planning, shared filesystem, subagents, custom long-term memory, and skills.

planning / todo
Coach tracks multi-step turns explicitly (check identity → load profile → call Retriever → call Designer → validate → respond → update memory). Also powers the interim status updates to the trainee.
virtual filesystem
Session-scoped state passing. Retriever writes chunks to file, Designer reads it and writes plan.md/plan.json, Coach reads plan.md to reply.This is short-term memory — resets each session.
subagents
Retriever and Program Designer are callable subagent tools from Coach. Retriever is also callable from Designer.
long-term memory store
Custom SQLite-backed store, replacing deepagents' default in-memory backend — reads/writes coach_memory and trainees at session start/end.

Data & embedding pipeline

The 600K+ Fitness Exercise & Workout Program dataset (Kaggle): 605,033 exercise entries plus 2,598 program summaries with goal/nutrition/difficulty narrative text. Not pre-chunked or pre-embedded — chunking and embedding both happen in this pipeline.

Qdrant payload schema

Metadata comes straight from the CSV columns, attached as payload rather than embedded into the vector — this is what the Retriever's slot-based filtering runs against.

Payload fieldSourceUsed by
source_tableexercises vs. program_summaryRetriever routes queries to the right sub-corpus

difficultyprogram_summary columnSlot filter + Designer's structural validation
equipmentexercise-level columnSlot filter + Designer's equipment-match check
