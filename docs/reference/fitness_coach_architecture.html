System overview

Coach is the trainee-facing main agent. It owns the conversation, identity resolution, and memory, and delegates to Retriever and Program Designer as subagents. Both subagents can call Retriever directly against Qdrant; Program Designer is the only agent that writes plans, backed by the SQLite trainee database.

01
subagent

Retriever agent

Callable by both Coach and Program Designer. Doesn't reason about fitness — its only job is accumulating enough grounded context to satisfy an information need, then handing back chunks with a confidence flag.

Accumulate-and-expand retrieval loop

Not a single retry loop — it tracks coverage of the overall information need across multiple sub-queries, expanding when gaps remain even after some sub-queries succeed.

  1. Decompose the needSlot-based extraction first (goal, equipment, difficulty, duration) — falls back to free-form LLM coverage judgment when the query doesn't map to slots cleanly.
  2. Pick next unaddressed need, query QdrantChunk count is adaptive to query specificity, not a fixed top-k.
  3. Validate against that specific needRelevant and sufficient, or noise?
  4. Sufficient → save to accumulated pool, mark need satisfied
  5. Insufficient → rewrite query, retry same need
  6. Re-check overall coverageGiven everything accumulated, is the original query now answerable? If not, formulate a new sub-query for the gap.
  7. Self-assess or hit ceiling → returnModel can surrender early if it believes coverage is sufficient; hard ceiling underneath as a safety net.
Hard ceiling5–6 total retrieval steps per invocation
CallersCoach (open-ended questions) + Program Designer (structured plan queries)
OutputAccumulated chunks + confidence flag
02
subagent

Program designer agent

Turns a goal plus retrieved chunks into a strict JSON plan. Synthesizes across multiple retrieved programs rather than selecting one — which means it needs a coherence guard.

New plan vs. revision

  1. Classify requestNew plan or revision to an existing one.
  2. New plan → call Retriever, then synthesize a draft by combining chunks across multiple retrieved programs.
  3. Revision → check plan.md / context first for what's needed (e.g. a knee-safe substitute); only call Retriever if that comes up empty.
  4. Structural validationRule-based, deterministic: equipment matches trainee's available equipment, rest days present, difficulty progression makes sense.
  5. Self-critique passLLM check for coherence, goal fit, and injury constraints — only triggered when synthesizing from multiple sources, since that's where conflicting programs can get mixed incoherently.
  6. Write plan.jsonStructured output + short change summary back to Coach.
Output schemagoal, difficulty, duration_weeks, equipment_available, weeks[days[exercises[name, sets, reps, rest_seconds, equipment, muscle_group, notes]]]
Revision guardInjury/limitation flags read from trainees table, not duplicated per plan
03
main agent

Coach agent

Owns the conversation, identity, routing, and long-term memory. Uses Designer as a tool rather than a hardcoded classifier — Coach reasons out whether a message needs Designer or can be handled directly.

Session start — identity resolution

  1. Check identityName + secondary ID (phone / email / trainee_id).
  2. Match → returning traineeLoad trainees profile, latest coach_memory summary, active plan. Name match without secondary ID match is treated as a mismatch worth confirming, not silently loaded.
  3. No match → new traineeRun intake flow: name, contact, goals, equipment, injuries/limitations → write first trainees row.
  4. Check progress_logs for missed-session patternsIf flagged, Coach opens the conversation proactively instead of waiting to be asked.

Per-message loop

  1. Load contextProfile, memory, active plan.
  2. Reason: handle directly or route to DesignerDirect: general coaching / knowledge questions, Coach may call Retriever itself. Routed: anything touching the plan itself.
  3. Interim acknowledgment before delegatingSent before a multi-step Retriever/Designer chain runs, so the trainee isn't staring at silence for 15–20s.
  4. RespondRelays Designer's structured output in trainee-facing language, or answers directly.
  5. Update memorySee long-term memory pipeline below. Also writes to progress_logs if the message contained loggable info.

05

deepagents wiring

Using the framework's primitives beyond plain tool-calling — planning, shared filesystem, subagents, and skills.

planning / todo
Coach tracks multi-step turns explicitly (check identity → load profile → call Retriever → call Designer → validate → respond → update memory). This is also what powers interim status updates to the trainee.
virtual filesystem
Session-scoped state passing. Retriever writes chunks to file, Designer reads it and writes plan.md / plan.json, Coach reads plan.md to reply.Short-term memory lives here — resets each session.
subagents
Retriever and Program Designer are callable subagent tools from Coach (the main agent). Retriever is also callable from Designer.
long-term memory store
Custom SQLite-backed store, replacing deepagents' default in-memory backend — reads/writes coach_memory and trainees at session start/end.
skills/retrieval-coverage-loop.md
Slot-based + free-form fallback coverage checking, accumulate-and-expand retry logic.
skills/plan-structural-validation.md
Deterministic rule checks: equipment match, rest days, difficulty progression.
skills/trainee-intake.md
New trainee onboarding script — what to collect, in what order, before Designer can build a first plan.
skills/plan-revision.md
Check-existing-first logic, when to patch vs. rebuild, when self-critique re-triggers.

Open items

Decisions deferred until the dataset is pulled and the build starts.

Blocks building
  • Qdrant payload schema — metadata fields the Retriever's slots need to filter on (goal, difficulty, equipment, muscle_group, duration)
  • Chunking strategy — depends on real dataset schema (program-level vs. exercise-level text)
  • LLM backend for the three agents — vLLM-served open model vs. Claude API
Safety / judgment
  • Injury/medical boundary — when Coach should say "see a doctor" instead of letting Designer quietly work around a symptom
  • Who can update injuries_limitations mid-conversation, and whether that needs a confirmation step
Deferred
  • Low-confidence Retriever result: best-effort plan with a flag, or Coach asks a clarifying question instead
  • Interface — FastAPI + chat UI, matching other NTA pipelines
  • Eval strategy before trusting the loop with real trainees
