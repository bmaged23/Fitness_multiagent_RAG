03 — relationships

Relationships

All foreign key relationships and their delete behaviour.

From To Cardinality On Delete Notes
trainees ──────▶ plans 1 → N CASCADE One trainee can have many plans (active, completed, archived). Active plan managed by Coach logic.
trainees ──────▶ coach_memory 1 → 1 CASCADE UNIQUE on trainee_id enforces exactly one memory row per trainee.
trainees ──────▶ progress_logs 1 → N CASCADE Logs persist across plans and span the trainee's full history.
plans ──────▶ plan_revisions 1 → N CASCADE Full audit trail. Previous and new plan_json kept on every revision.
plans - - - ▶ progress_logs 1 → N SET NULL Nullable FK. Logs survive if the plan is archived or deleted — plan_id becomes NULL.
04 — constraints & indexes

Constraints & Indexes

Every CHECK constraint, composite unique constraint, and index defined in the schema.

UQ trainees — (name, secondary_id) Name alone is never sufficient for identity. Both fields required to uniquely identify a trainee.
CHK plans.status — IN ('active', 'completed', 'archived') Prevents invalid status strings at the DB layer regardless of Coach logic.
IDX idx_plans_trainee_status — plans(trainee_id, status) Fast lookup of a trainee's active plan — the most frequent Coach query on this table.
UQ plan_revisions — (plan_id, revision_number) Prevents duplicate revision numbers for the same plan.
CHK plan_revisions.triggered_by — IN ('user_request', 'self_critique', 'validation_fix') Tracks the cause of each revision — user-initiated, Designer self-critique, or structural validation fix.
IDX idx_progress_logs_trainee_date — progress_logs(trainee_id, log_date) Coach scans recent logs at session start to detect missed-session patterns.
UQ coach_memory.trainee_id Guarantees exactly one memory row per trainee — INSERT … ON CONFLICT REPLACE is safe.
